# Share kit (§6.10): Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give therapists a share page at `/dashboard/profile/share`: link with WhatsApp share, QR code download, a professional one-page PDF (paid plans), and an email signature.

**Architecture:** API (NestJS, `apps/api`) generates the QR code and the PDF server-side, from the signed-in user's own profile. The app (`apps/app`, Vite React) adds a "Share" tab to the existing tabbed `/dashboard/profile` page. Every link is built with `profilePath(handle)`, never by joining strings.

**Tech Stack:** TypeScript, NestJS, Prisma, `pdfkit` (already a dependency of the API), `qrcode` (new, API only), React, Vitest.

**Spec:** `docs/unclutter-desk-v2-spec.md` §6.10, §5.3 (profile entitlements), and the Phase 1 acceptance line "Share link, QR and PDF use `profilePath()`; PDF gated by profile entitlements".

- **Enterprise grade, no workarounds:** use the real shared components (`EntitlementsService`, `StorageService`, `UpgradePrompt`, the app's API client). Tests fake only the network.
- Stay out of `apps/api/src/modules/admin/` and `apps/profiles/`: other branches are working there.

## Review Focus

1. A Free user calls the PDF endpoint: **402** `ENTITLEMENT_REQUIRED` with `feature: 'downloadablePdf'`, from `EntitlementsService.assertProfile`, and the app shows the locked preview and upgrade prompt, not an error.
2. Every URL in the QR code, PDF, WhatsApp message and email signature equals `profilePath(handle)` / `${PROFILE_PUBLIC_ORIGIN}/${handle}`.
3. The email signature escapes every value: a name like `<script>alert(1)</script> & "Co"` comes out inert.
4. A user can only ever get their own QR and PDF: there's no handle or id in the request.
5. A profile with no photo still produces a good PDF (initials instead of the photo).

### Task 1: QR code endpoint

**Files:**
- Modify: `apps/api/package.json` (add `qrcode` and `@types/qrcode`)
- Create: `apps/api/src/modules/practitioner-profile/share/qr.ts`
- Modify: `apps/api/src/modules/practitioner-profile/practitioner-profile.controller.ts`
- Test: `apps/api/src/modules/practitioner-profile/share/qr.spec.ts`

- [ ] **Step 1: Write failing tests** for a pure function `profileQr(url: string, format: 'svg' | 'png'): Promise<Buffer | string>`:
  - the SVG is valid SVG and has no `<script>`;
  - the PNG starts with the PNG signature bytes;
  - it refuses a URL that isn't `https://` (throws).
- [ ] **Step 2:** Run them; they fail.
- [ ] **Step 3: Implement** with `qrcode` (`toString(url, { type: 'svg', errorCorrectionLevel: 'M', margin: 2 })` and `toBuffer` for PNG, width 1024).
- [ ] **Step 4: Endpoint** `GET /v1/practitioner-profile/me/share/qr?format=svg|png` on the existing controller (it already has `JwtAuthGuard, RolesGuard`). It loads the caller's own profile handle, builds the URL with `PROFILE_PUBLIC_ORIGIN`, and responds with `Content-Type: image/svg+xml` or `image/png`, `Content-Disposition: attachment; filename="<handle>-qr.<ext>"` and `Cache-Control: private, no-store`. 404 if the user has no profile. Any other `format` is a 400.
- [ ] **Step 5:** Add an access test next to `practitioner-profile.access.spec.ts` showing the route is authenticated. Run the API suite and typecheck; commit `Phase 1: share kit QR code`.

### Task 2: Profile PDF

**Files:**
- Modify: `apps/api/src/modules/storage/storage.service.ts` (add `get(bucket, key): Promise<Buffer | null>`, using the S3 `GetObjectCommand` like the existing methods; `null` on not found)
- Create: `apps/api/src/modules/practitioner-profile/share/profile-pdf.ts`
- Modify: the controller
- Test: `apps/api/src/modules/practitioner-profile/share/profile-pdf.spec.ts`, plus a `get` test in the storage spec

- [ ] **Step 1: Write failing tests** for `renderProfilePdf(input): Promise<Buffer>`, where `input` holds name, kind label, headline, city/country, qualifications text, primary and other specialty labels, language labels, the profile URL, a QR PNG buffer, an optional photo buffer, and the theme tokens from `packages/ui/src/brand/profileThemes.ts` (`themeKey` on the profile):
  - the output starts with `%PDF-` and is one A4 page;
  - the name, the URL and the specialties appear in the text (check with `pdf-parse` as a dev dependency, or read the uncompressed stream with `compress: false` in tests);
  - with no photo it draws initials and doesn't throw;
  - a 3,000-character qualifications text is cut to fit with an ellipsis and stays one page.
- [ ] **Step 2:** Run them; they fail.
- [ ] **Step 3: Implement** with `pdfkit`. Layout: header band in the theme's primary colour; round photo or initials; name, kind, headline, place; qualifications; specialties; languages; QR (35 mm) with the URL under it. Use pdfkit's built-in Helvetica (no font downloads). Plain text only.
- [ ] **Step 4: Endpoint** `GET /v1/practitioner-profile/me/share/pdf`. First `await entitlements.assertProfile(userId, 'downloadablePdf')` (it throws the 402). Then load the profile and its taxonomy labels, get the photo with `StorageService.get` from the public bucket (skip the photo if it's missing or the call fails; log at warn), make the QR PNG with Task 1's function, render, and respond `application/pdf`, `attachment; filename="<handle>-profile.pdf"`, `private, no-store`.
- [ ] **Step 5:** Tests for the endpoint: a Free user gets the 402 and no PDF work is done; a paid user gets a PDF. Use the real `EntitlementsService` against the test database pattern the other entitlement specs use. Commit `Phase 1: share kit profile PDF (profile entitlements)`.
